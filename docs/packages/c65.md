# c65: Chrome 101 fallbacks (curie, opus, branch `wp/curie-chrome101`)
**Why:** `c60` runs milestone A on the Samsung S8+, whose Chrome 101 is also its WebView and stays at 101 (nordmu,
2026-11-03). nordmu, 2026-11-04: c60 is split; this package is its laptop half, so the phone run only executes and
measures. **Laptop only:** it runs at night with no phone; never call adb, not even `adb devices` (tests that need adb
put a fake one on `PATH`). What a survey on `phase-0` found:
- `100dvh` (Chrome 108) in the full-height screens' rules, with no fallback, so on 101 `.mark`, `.result` and
  `.detail` lose their height. `d62` (queued before this package) moves the height into one token in tokens.css,
  `--screen-h: calc(100dvh - var(--inset-top))`, and leaves the Chrome 101 fallback to this package. A `100vh` line
  before a declaration that holds `var()` doesn't work (such a declaration is found invalid only when computed, and
  then falls back to `unset`, not to the line before), so the fallback for the token is
  `@supports not (height: 100dvh)`.
- app/src/media/decode.mjs feeds the next chunk when the decoder's `dequeue` event (Chrome 106) or an output wakes the
  loop. Without the event, the stepper's stream (`STREAM_QUEUES` in `stepper.mjs`: one chunk at a time) waits for an
  output that a decoder holding B-frames back never gives: tests/app/fake-webcodecs.js's decoder (`reorder` 3) with
  its `dequeue` events off gives 0 frames and `decode-stalled` after `stallMs`; with them on, all 30.
- No syntax newer than 101 in what ships: every shipped JS file (app/src, the vendored htm, preact and mediabunny,
  sw.js, src/'s diagnostics.js and track/) comes out of esbuild's transform with `target: 'chrome101'` the same as
  with `esnext`; the TF.js bundle is built at `target: 'es2020'` (`build-tfjs.mjs` in app/tools/). No `:has()`,
  container queries, CSS nesting, `color-mix`, popover, `structuredClone`, `findLast`, `Promise.withResolvers` or
  top-level await either.
- Not known from the laptop: OPFS on Android's Chrome 101 (`getDirectory`, `createWritable`; the store,
  `store.mjs` in app/src/store/, has no fallback without them), whether 101 accepts the capture's encoder configs
  (`hardwareAcceleration: 'no-preference'`, `latencyMode`; `capture.mjs` in app/src/media/, `start()`), and
  `MediaStreamTrackProcessor` there. c60 checks them with this package's probe.
- The phone tools name the Fairphone: spike/pose-bench/phone-sample.sh always samples `4d42e62f`, and
  app/tools/check-media-apk.mjs finds the decoder's name only among Codec2's `c2.…` names; Android 9 has OMX ones
  (`OMX.Exynos…`). Its `idle1320-` is the Fairphone's M size (440 × its pixel ratio 3), not another phone's.
The Chrome versions above and in step 1 are from memory and MDN; c60 checks each on the phone. Where this package
writes one down, it says so.

2. The decode loop without `dequeue`. Red first: an option of the fake decoder that fires no `dequeue` event and has
   no `ondequeue` property (Chrome before 106), with its `reorder` holding B-frames back, and the stepper's stream on
   it (decodeFrames with `maxQueued` 1, `maxQueueSize` 1, and a stepper on a fake source) gets every frame with no
   `decode-stalled`. It fails on `phase-0`. Give the fake's normal mode an `ondequeue` property, as Chrome 106+ has,
   if the fix detects the event that way. The fix in decode.mjs, only where the decoder has no `dequeue` event: wake
   the loop another way, a short re-check of `decodeQueueSize` while it waits (a timer, never a busy loop), or on
   whatever else shows a chunk was taken. Where the event exists nothing changes: no timer runs (a test says so), and
   the stepper's timing stays: run `check-media.mjs` (in app/tools/) in a `devlock.sh slice` (in pipeline/; headless
   Brave has the event) and give s38f1's step times beside it (steps back to back 19.0 and 15.3 ms on k1, 23.5 and
   23.4 ms on k2to5 with `--clips ~/.cache/coach/c34-clips`, made by `make-phone-clips.sh` (app/tools/) in slices
   and deleted after; a step to a held frame 0 ms, p90 0.1 ms). `c64` comes after this package and builds on this loop.
