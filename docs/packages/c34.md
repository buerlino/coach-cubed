# c34: the frame source and the cut on the phone (curie, opus, branch `wp/curie-media-phone`)
**Why:** s9's frame source and s32's cut were measured only in headless Brave on the laptop (software decoding; their
reports, `git log --grep '^s9: report'` and `--grep '^s32: report'`). M1–M3's one-frame steps, the analysis's decode and
the cut's memory all rest on numbers nobody has taken on the phone. nordmu moved them out of c26 on 2026-11-02 so they
arrive before the screens build on them; c26 keeps the measurements that need the screens. None of these needs a
screen: c20's debug check page runs them.
**Read:** app/README.md ("The frame source" and "Keeping the video" are past its first 400 lines: read them by
section); app/src/media/frame-source.mjs (`openFrameSource(blob)`, `frameAt`, `frames`, `frameTimes`);
app/src/media/cut.mjs (`cutVideo`, `keepVideo`); app/tools/check-media.mjs (s9's headless check, the model for the
runs); c20's shell: app/tools/build-apk.sh (the debug APK), app/debug/check.mjs (the check page, debug builds only),
app/tools/check-apk.mjs (installs the APK and drives the check page over the WebView's DevTools: a clip copied into the
app's own `files/` with run-as and set on the page's input with `DOM.setFileInputFiles`, no picker), app/README.md
("The Android shell") and c20's report (`git log --grep '^c20: report'`: the phone, its WebView and the engine's
numbers); docs/pipeline.md ("The phone").
1. The clips, made on the laptop with ffmpeg into a cache outside the repo (never committed, never the owner's camera
   files), each command in the report: 1080p H.264 at 30 fps, 60 s, a keyframe every 1 s; the same with keyframes every
   2–5 s (as phone cameras write); a 60 fps one; a portrait one with a rotation-90 flag; a variable-frame-rate one; an
   HEVC one; and one of about 100 MB. Heavy encodes go through `pipeline/devlock.sh slice`.
2. On the Fairphone, by day (nordmu knows the run is happening): the phone's lock, `adb -s 4d42e62f` only,
   `pipeline/stay-awake.sh 4d42e62f`. pascaline's day runs use the same phone and lock: do the laptop work (clips,
   page, APK) first, then take the lock with its 30-minute wait (`pipeline/devlock.sh acquire 4d42e62f curie-<run>
   1800`), up to three times. If it stays busy or the phone is missing, say so in the report and stop. The
   clips go into the app's own `files/` for the run, as check-apk.mjs does with the test clip, and go with the app;
   install c20's debug APK and run the measurements from its check page, extended for them and driven by check-apk.mjs
   (or a sibling tool) over the WebView's DevTools (no taps: if a step needs one, say so and skip it). The check page
   stays in the debug build only: the shipped `dist/` stays without it.
3. Measure, each the median of at least five runs, with the device, Android and WebView versions and the build:
   - decode rate of a 60 s range (frames per second), with a consumer that closes each frame at once and with one that
     takes 100 ms a frame (the backpressure);
   - `frameAt(t)` at 20 random times, keyframes every 1 s and every 2–5 s;
   - stepping +1 frame 30 times with `frameAt` (M1–M3's step: it decodes from the keyframe every call);
   - the canvas turn's cost per frame for the rotation-90 file at 30 and 60 fps;
   - `openFrameSource` of the 100 MB file (the packet listing);
   - the HEVC file: the error code, or that it decodes;
   - the 60 fps and variable-rate files: `info.fps` and the spacing of `frameTimes`;
   - the memory with the decoder running (`spike/pose-bench/phone-sample.sh`, or the WebView's own numbers);
   - `cutVideo` of a 60 s range of the 1080p file: its time and the memory it peaks at (the cut is built in memory
     before it is saved), and `keepVideo`'s write into OPFS; then the cut opened with `openFrameSource` and decoded
     end to end on the phone (s32: no real decoder has opened a cut yet).
4. The numbers into app/README.md: a short "On the phone" part in "The frame source" and in "Keeping the video", each
   number with how it was measured. Where a number says a plan won't hold (say, a step takes over 200 ms, or the cut
   of a minute needs more memory than the WebView gives), say so under "Needs a decision" with a recommendation.
5. Put the phone back: `pipeline/stay-awake.sh 4d42e62f --restore-real`, the app uninstalled, the clips deleted, no
   `adb -s 4d42e62f reverse` or `forward` left.
**Done when:**
