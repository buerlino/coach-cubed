# s11: the scoring adapter (schrödinger, sonnet, branch `wp/schroedinger-scoring-adapter`)
**Why:** The UI draws cues from one view model (contract 4), so a new cue in `diagnostics.js` needs no UI change
(docs/ui-design.md, "Keeping the UI maintainable"). Honest verdicts must reach the screen: a cue that can't be scored
says why in the engine's words, and every unvalidated threshold says provisional (rules-core.md, principle 1).
**Read:** docs/app-plan.md ("The contracts", "The pieces"); docs/ui-design.md ("The look"; A1 and A2 in "The screens");
tests/loadDiagnostics.js; tests/diagnostics.test.js; src/track/smoothing.mjs; tests/track.test.js; app/README.md; the
cue view model's contract in `app/src/contracts/`; s4's API on the `Diagnostics` object (`diagnostics.js` in `src/`).
**Red first:** yes
1. Tests first, `tests/app/scoring.test.js`: with smoothing off, every committed fixture track gives its golden's verdicts
   and values through the adapter; with the app's default smoothing, the same result as `src/track/`'s smoothing (pinned
   to the old page by tests/track.test.js) followed by `computeResults()`; a track too short or without a body scale
   gives "can't score" with the engine's reason for every cue; the status words map from the verdict levels and from
   errors; every cue carries its provisional flag; the lift window and the worst moments are in seconds. They fail on
   phase-0.
2. `app/src/scoring/`: `diagnostics.js` loaded as the classic script it is (in the app through index.html, in Node through
   tests/loadDiagnostics.js), `setPage(lift)`, smoothing first with its σ in the notes, `computeResults()`, then the view
   model through s4's API. A plain module with no DOM.
3. Say in the report what the goldens score (raw tracks; docs/backlog.md, "Unverified") and what the adapter's tests pin.
**Done when:**
- the view model passes contract 4's validator; every string on it comes from `diagnostics.js`, none from the adapter;
- `npm test`, `npm --prefix app test` and the Python tests pass.
