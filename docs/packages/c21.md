# c21: the page test, offline (curie, sonnet, branch `wp/curie-page-test`)
**Why:** Step 5.6 asks for a headless page test that loads the app offline, runs a lateral raise and a snatch, and fails
on any console error, 404 or empty cue list; the pipeline runs it as `npm --prefix app run test:page` once the script
exists, on every run that touches `app/` or `src/`. So it must be quick and run in a pipeline worktree, which has no
example clips and none of the gitignored TF.js bundle or weights, on a laptop shared with pascaline's nights. A
non-empty list proves little: the cards must say what the scoring says.
**Read:** docs/app-plan.md ("The build"); app/README.md; app/package.json; app/tools/assemble.mjs; app/tools/serve.mjs;
spike/pose-bench/run-cdp.mjs; tests/fixtures/README.md; tests/README.md; app/src/pose/pose-client.mjs,
app/src/pose/pose-worker.mjs and app/src/pose/worker-core.mjs (contract 1's messages); app/src/analysis/job.mjs and
app/src/analysis/queue.mjs; app/src/scoring/score.mjs; c19's offline check app/tools/check-offline.mjs (reuse what fits);
the flow the test walks, as d13–d17 built it: app/src/flow/flow.mjs, app/src/ui/screens/H.mjs, app/src/ui/screens/Import.mjs,
app/src/ui/screens/M.mjs, app/src/ui/screens/Q1.mjs and app/src/ui/screens/A1.mjs; A1's cards come from
app/src/ui/result-model.mjs (`cardsOf`, d17), each card a `.cue-card` with `data-cue`, so step 3 can compare per cue id.
1. The test build: an assemble option whose replay engine answers the k-th decoded frame with the k-th frame of a
   committed fixture track, through contract 1's messages. In the test build the job takes the fixture's `meta` (width,
   height, fps). The shipped `dist/` never contains the replay engine, and the test build needs neither
   `app/vendor/tfjs/` nor `app/models/`.
2. Clips of its own, matched to the replayed tracks: two ffmpeg `testsrc2` clips, committed in `tests/app/clips/`, the
   command in tests/README.md:
   - for `example/lateral-raise-cable-1`: 25 fps, 75 frames;
   - for `example/athlete-a-trim` (the snatch): 30 fps, 107 frames;
   - both portrait 9:16 at a small size such as 108×192, so a few kB each.
3. `app/tools/page-test.mjs` and the `test:page` script: assemble the test build, serve it on `$COACH_PORT`, headless
   Brave or Chromium over CDP (found, or given by an option; this laptop has `/usr/bin/brave-browser`), go offline after
   the first load, then H, import, mark, analyse, result for both lifts, the clips decoded for real. Each lift's cue
   cards (the status word per cue) must equal the view model of s11's adapter, computed in Node from the same fixture
   track. No browser found fails with a clear line, unless `COACH_PAGE_TEST_SKIP=1` is set.
4. It fails on a console error, a failed request, an unhandled rejection, a job that doesn't finish in its time, or cards
   that differ from the adapter's.
5. An optional mode, off by default: the real engine on the example clips, the CPU backend, one clip per
   `pipeline/devlock.sh slice` (never `acquire host-cpu`), the clips read from the `phase-0` worktree's
   `tests/fixtures/local/` (found with `git worktree list`; read-only, never copied). Say in the report whether you ran
   it; real clips on the phone are c26's.
**Done when:**
- `npm --prefix app run test:page` passes in under a minute in a fresh worktree without `app/vendor/tfjs/` and
  `app/models/`;
- it fails on a console error, a failed request, an unhandled rejection, a job that doesn't finish, or cards that differ
  from the adapter's (say how you checked each);
- the shipped `dist/` (assemble without the test option) has no replay engine and no fixture track;
- `npm test`, `npm --prefix app test` and the Python tests pass.
